## What is new in the runner

**Quota is the real cost.** The worker authenticates through ChatGPT login
(`auth_mode chatgpt`), so a replay is paid for in **plan quota**, not dollars.
Every dollar figure in this report and in every earlier one is a shadow cost.
`scripts/replay-01a07e54.ts` now calls `account/rateLimits/read`
(app-server-protocol `src/protocol/common.rs:1234`) immediately before the first
scripted user turn and again immediately after the last, and stores both
snapshots — `usedPercent`, `windowDurationMins`, `resetsAt` per window, plus
wall clock — and the delta in `replay.json`. `resetsAt` is compared across the
two reads, so a window that rolls over mid-run marks **its own delta invalid**
rather than reporting a difference between two different windows.

**`pgrep -af codex` at both ends**, recorded in the same block. This matters
more than expected: see [the concurrency problem](#the-concurrency-problem).

**`--arm <name>`** calls `src/arms.ts`'s `prepareArm` once, after
`thread/inject_items` and before the first scripted user turn. Wiring only.
The post-preparation history size is then re-measured with the product's own
counter (`thread/shake/preview`, which never mutates) and stored as
`historyTokensAfterArm`, so an arm's actual starting context is recorded rather
than inferred from the preview it was planned from.

**`--service-tier fast`.** Two channels, because either can silently miss:
`service_tier = "fast"` in the worker's `config.toml`, and `serviceTier` on
`thread/start`. Config.toml stores the tier as `fast`
(`core/src/config/edit.rs:235-247`) while the value that reaches the model API
is `priority` (`protocol/src/config_types.rs:527-552`,
`ServiceTier::Fast.request_value()`). The model id does not change: there is no
`gpt-6-astra-fast` slug, only `service_tiers: [{ id: "priority", name: "Fast" }]`
on the one `gpt-6-astra` entry.

**The tier verifiably applied on all three runs.** `thread/start`'s *response*
echoes the resolved tier (`app-server-protocol v2/thread.rs:185`), and all three
runs logged `service tier: requested fast, server reports "priority"`. That is
the authoritative channel. Note that `config/read` reports
`service_tier: null` even with the key present in the file the worker loaded —
so **do not verify the tier through `config/read`**; it did not surface the key
here.

**Fast-tier pricing was unknown when this report was first written; it is now
known, and every cost line below has been recomputed** (2026-09-12). The worker
authenticates through ChatGPT login on a Pro plan, so the real unit is **Codex
credits**, and the official Codex pricing page
(<https://learn.chatgpt.com/docs/pricing>, fetched **2026-09-12**) publishes
them for gpt-6-astra: **250 credits per 1M input, 25 per 1M cached input, 1,250
per 1M output**, and *"Fast mode applies a 2.5x multiplier to Astra's Standard
rate."* There is **no long-context multiplier and no cache-write charge in
Codex** — the 272K 2x/1.5x terms in `pricing.json` belong to the API rate card
and apply to API billing only.

So every table below carries **two** cost lines and they are not
interchangeable:

- **API shadow $** — the API rate card, long-context aware, summed per request.
  A comparison unit. **Nobody was billed this.**
- **Codex credits** — the plan rate card, at standard and at Fast. This is what
  the runs actually spent. All four arms ran Fast, so their Fast column is the
  real one; run 9 ran standard.

`pricing.json` now carries both as named profiles (`api`, `codex-credits`);
`scripts/pricing_lib.py` is the one implementation both Python reporters use,
and `npm run estimate -- --profile codex-credits --tier fast` prices a scenario
in credits.

### Three findings that matter more than the table

**1. Shake cut cost — 4.8x on the API card, 2.4x in the credits actually
spent — and lost nothing measurable.** A's `$12.37` against B's `$59.46`, on the
same task, same script, same tier, both ACCEPTED at 12 of 12. **The 4.8x is
API-only.** In Codex credits, the unit this run was really charged in, A spent
**773** against B's **1,870**: a **2.4x** reduction (**2.3x** against the mean
of B and B2, 1,777). The gap between the two ratios is the long-context
multiplier, which exists on the API card and does not exist in Codex: on the API
card B pays 2x on every input and cached-input token and A pays none, which
doubles the measured effect. Credits price both arms on the same flat card, so
what remains — still a 2.3x saving — is the token reduction alone. The mechanism is exactly the one §11.12 predicted, **for the API figure**: A's
requests run 152,140 → 216,055 input tokens, every one of them **below** the
272,000-token long-context threshold, so none of them pays the 2x input / 2x
cached / 1.5x output multiplier. B's 44 requests are all above it. In credits
that mechanism is absent — there is no threshold — and the saving comes purely
from A sending about a third as many tokens: 13.6 credits per request after
request 1, against B's 36.0. A was also the *fastest*
run of the three at 454 s of worker turns, against run 9's 757 s.

The predicted counterweight did not appear in cost: A took **51 requests to
B's 44**, the most of any run, so elision did cost extra round trips — but a
smaller request is cheap on either card. The §11.12 estimate for this arm was
$12–18. It came in at $12.37, i.e. 773 credits on Fast.

Both shake arms land in the same place: A at $12.37 and C at $14.63 against
B's $59.46, a **4.1–4.8x** reduction **on the API card only**; in Codex credits
it is 773 and 914 against 1,870, a **2.0–2.4x** reduction (≈2.3x for A and
≈1.9x for C against the B/B2 mean). Read the 2.0–2.4x as the result and the
4.1–4.8x as an API-billing artefact. All three ACCEPTED at 12 of 12.

**2. The retrieval arm made zero retrieval calls — and so did every arm.** `read_artifact` was
registered and available in A, 348,590 tokens of tool output had just been
elided out from under the worker, and it paged **none** of it back. Verified two
ways in the worker's own rollout: zero top-level tool calls named
`read_artifact`, and zero `tools.read_artifact` calls from inside code mode —
which is the form that would have been used, since every one of this worker's
860 tool calls is an `exec` into code mode.

This makes arm C's contrast structurally uninformative on this task, and that is
how it landed: C also made zero. You cannot withhold a tool that was not being
used. **It also
means the `item/completed` retrieval counter over-counts badly and must not be
quoted.** It reports 4 for A and 7 for B, all false positives, because the
replayed task *is the artifact reader*: 69 `exec` bodies mention `read_artifact`
while writing `read_artifact.rs`, and the scripted user's own turn 4 says the
words out loud. `scripts/arms-row.py` therefore counts retrieval from the
rollout with two exact signatures, and the runner's `readArtifactCalls` block
carries the over-count with a note rather than a number anyone should use.

**3. The compaction assertion has a false positive on the shake arms, and A
tripped it.** A exited 2 with `COMPACTION ASSERTION FAILED` on a single
violation: `compaction event in the worker rollout at 06:02:35.503Z`. That
record is written by the **shake itself**, 0.8 s after the shake's own internal
`auto-compact-0` turn and **7.2 s before request 1 exists**:

```
06:02:34.707Z  auto-compact-0 turn context   (the injection's internal turn)
06:02:35.503Z  "compacted" record            <-- the violation
06:02:42.735Z  request 1                     (152,140 input, 0 cached)
```

A did not compact during the run: its 51 requests climb monotonically
152,140 → 216,055 with **zero input-token drops** and no second `compacted`
record. B, the same harness with no shake, produced **zero** compaction events,
which pins the record on the shake rather than on injection. C reproduced it exactly — one `compacted` record at 06:25:42.714Z, 7.9 s before
its own request 1, no drops, 59 monotonic requests — so this is a property of the
shake arms, not a one-off. So: A and C are full-context runs, their exit code 2 is
a harness false positive, and **the assertion needs to ignore a `compacted`
record that predates the first model request when an arm was prepared.**

**Fixed 2026-09-12.** `checkCompaction` now excuses a `compacted` record only
when BOTH hold: it precedes the arm's first model request, and it carries the
shake path's own marker `"[shake] context reduced surgically"` (the message the
record was already writing, which is what makes the two paths distinguishable).
Either condition alone is still a violation: an unmarked pre-request record
means the injected history really was compacted before the arm began, and a
marked record after the first request means history was rewritten mid-run.
Compaction after the arm's first request and >50% input drops fail exactly as
before. Re-run over the four preserved rollouts: **A and C now PASS with the
record recorded and marked `ignored`, B and B2 are unchanged** — the fix moved
the two false positives and nothing else. Unit tests in
`src/compaction.test.ts` cover a synthetic shake-then-clean sequence, a
synthetic real compaction (record plus input cliff), both half-excused cases,
and a warm-cache priming request.

- **Cannot say** any of it cleanly at all, because of the next section.

## <a id="the-concurrency-problem"></a>The concurrency problem

`pgrep -af codex` counted **36 codex processes alive at the start of run A and
52 at the end of run B.** These are the operator's own long-lived sessions
(`.../harness-repo/current/codex --dangerously-bypass-approvals-and-sandbox`,
plus `codex-code-mode-host` children across releases 0.153.2, 0.153.4 and
0.154.0). They authenticate as the same ChatGPT account and spend the same plan
quota.

Every quota delta in this report is therefore an **upper bound on what the run
itself cost**, not a measurement of it. The count rising within each run
(36 → 43, 41 → 52) shows sessions starting while the replay was in flight. The
census is recorded in each `replay.json` so this is documented rather than
guessed — which was the point of recording it — but it is not corrected for, and
it cannot be corrected for after the fact.

**A clean quota number needs a quiet host.** That is the single largest
methodological debt this report leaves behind, and it is cheap to fix: run the
matrix with no other codex sessions alive and assert the census is empty before
starting.

### What the windows actually are

The server reports **one** window, not two:

- **primary**: `windowDurationMins = 10080` — a **7-day** window, resetting
  `2026-09-15T01:22:07Z`. Identical in the before and after read of all runs, so
  `resetCrossed = false` and **every delta below is valid**; no run crossed a
  reset.
- **secondary**: **absent** on every read, in every run. `RateLimitSnapshot`
  has the field (`v2/account.rs:565`); this account's snapshot does not populate
  it.

Worth stating plainly because it contradicts the premise the session was
scheduled against: **there is no ~1-hour window visible in this channel.** The
only window the app-server reported resets four days out. Whatever shorter limit
was expected, `account/rateLimits/read` did not show it, so "finish before the
reset" was not a constraint these runs were ever actually under. Total spend
across all three runs moved the 7-day window from 56% to 67%.

## Arm C is propensity, not capability

Arm C is labelled **prompt-discouraged**, and that label is load-bearing. The
worker keeps a real tool registry with `read_artifact` in it and is *asked* not
to use it. The number it produces is the model's propensity to obey, not the
effect of withholding retrieval. §11.12 blocker 1 is **still open**.

`src/arms.ts`'s `promptVariant()` already existed but **nothing in the replay
runner read it** — so before this batch, `--arm shake-elide-noread` would have
been a byte-identical replicate of `--arm shake-elide` with a different label.
That was caught and fixed mid-session (commit `702031f`); the first launch of
run C was discarded and relaunched. `replay.json` now records `promptVariant`
and `noreadIsPromptOnly` so no future reader can mistake this for a capability
test. The synthetic benchmark's own `NOREAD_HINT` ("Do not call any tools",
`src/convert.ts:202`) could not be reused: the replay worker has to run the
stubbed toolchain to do any work at all, so the ban is narrowed to the one tool.

**What C actually did: nothing different.** It made **zero** `read_artifact`
calls — the same zero as A, which had the tool and was never told not to use it.
So the prompt ban changed no behaviour that can be observed, because there was no
behaviour to suppress. C was ACCEPTED at 12 of 12 like the other two. It did cost
more than A — 59 requests against 51, $14.63 against $12.37, 604 s against
454 s — but with n = 1 per arm and the instruction text as the only difference,
that gap is indistinguishable from run-to-run variance in the worker. **Read it
as a second sample of the shake arm, not as a retrieval-withheld result.**

C's injected history measures 536,461 tokens against A's 536,363 — the fixture is
byte-identical, and the 98-token difference is the extra developer instruction,
since `thread/shake/preview` counts the whole thread including instructions.

**The capability version is reachable, and now located.** Registration is conditional
on the thread being durable — `core/src/tools/spec_plan.rs`:

```rust
// Artifact recovery uses durable thread storage. Ephemeral threads,
// including tool-free structured requests, do not expose it.
if !context.turn_context.config.ephemeral {
    registry.add(ReadArtifactHandler);
}
```

so `ephemeral: true` on `thread/start` (`v2/thread.rs:114`) removes
`ReadArtifactHandler` from the registry outright — the model never sees the tool.
There is no artifact-specific config key or feature flag, and no
allowlist/denylist field on `thread/start` or `turn/start`. The installed
0.153.4 binary carries this condition.

It was **not** used here, for two reasons that each need a run to settle:

1. An ephemeral thread is not persisted to disk, and that rollout is where this
   harness reads per-request token usage and the entire compaction assertion
   from. A capability arm would come with no cost breakdown and no full-context
   guarantee unless the runner first learns to derive both from the
   `thread/tokenUsage/updated` notifications it already collects in
   `usageByTurn`.
2. Shake's own elision is documented against durable thread storage in the same
   comment, so **the shake arms may not be available on an ephemeral thread at
   all** — which would make the combination this arm needs impossible rather
   than merely awkward.

Both are cheap to check and neither was affordable inside this session.
