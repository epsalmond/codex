# Warm-cache matrix — 2026-09-12

Five runs, strictly sequential, executed against the plan in
[plan-warm.md](plan-warm.md). **Standard tier** (the operator's call: no
`--service-tier`, so `thread/start` sends no `serviceTier` and the worker config
carries no `service_tier` key — the server echoes `null`). Everything the
2026-09-11 arm matrix held constant is still constant: Tier C flattened history
(`fixtures/01a07e54-r264-redacted-trimC.flattened.json`, 907 items, 2,013,767
bytes), the frozen six-turn scripted user v1, `model_context_window = 872000`,
the bubblewrap jail, the stubbed toolchain, and a worktree reset from
`$BENCH_CHECKPOINTS/01a07e54-r264` and verified **REJECTED at 12**
before every launch.

**Rows are generated, not transcribed.** `scripts/run-warm-arm.sh` runs one arm
end to end and `scripts/warm-row.py` reads the row out of the run's own
`replay.json`, rollout-activity verdict and classified census.

**The four arms in [arms-2026-09-11.md](../2026-09-11/arms-2026-09-11.md) were
Fast tier; these are standard.** Credit totals are therefore 2.5x apart for
purely tariff reasons — the "credits (fast equiv)" column restates each run at
Fast rates so it can be compared with that report directly.

**Quota attributability.** Sixteen personal-account codex processes were alive
throughout (idle foreground TUIs on ptys; the operator classified them as effectively
inactive and none was killed), so `--allow-busy-host` was passed for every run.
Being alive is not spending: each run snapshots every `$CODEX_HOME/sessions`
rollout mtime before and after, and a run whose window saw another session write
a rollout has its quota column marked **unattributable**. That check is the
evidence the process count cannot give.

**Two harness notes from this run, before any more are launched.**

1. **The 7-day window rolled over between the dry run and this run.** The dry
   run at 01:01 read `primary 82%`, resetting `2026-09-15T01:22:07Z`; this run
   read `0%` before its first turn, resetting `2026-09-19T08:10:21Z`. So the
   window this channel reports did reset, four days earlier than the old
   `resetsAt` predicted, and the batch is nowhere near a ceiling.
2. **`resetCrossed` false-positives on a sliding window.** This run's two reads
   report `resetsAt` 7 seconds apart (08:10:21 → 08:10:28), so the equality test
   that exists to invalidate a delta spanning a reset marked a perfectly good
   +2 pp delta invalid. The window is evidently sliding, not fixed. The check
   needs a tolerance (a reset is crossed when `resetsAt` moves by roughly the
   window duration, not by any amount at all) — **not changed mid-batch**, so
   every quota delta in this table carries the flag as recorded and the +2 pp
   should be read as valid.

**Run (b) is the first arm in this benchmark that was not accepted, and it is a
worker result rather than a harness one.** A2 is a straight repeat of arm A
(shake + retrieval, cold) on the standard tier, and it came back **REJECTED at 1
of 12**: `E2 rate_limits.rs no longer clones a Copy timestamp` — the worker left
`format_reset_timestamp(dt.clone(), captured_at)` in place, the one check A
cleared. Everything else passed, the run was full-context, and the worker's own
closing message describes finishing the work. So with n = 2 the shake+retrieval
arm is **1 accepted, 1 rejected at a single check**, which is the first evidence
in this matrix that acceptance itself varies run to run — the A row's 12/12 was
being read as a property of the arm, and it is not one. It says nothing about
shake: A2 elided the same 360,528 tokens and made the same **zero**
`read_artifact` calls.

**The priming mechanism works, first time, exactly as designed.** Run (c)'s
priming request sent **516,251 input tokens with 0 cached** and got back five
output tokens (`ready`) in 14 s, and the arm's request 1 then found
**516,096 of 516,315 input tokens cached — a fraction of 0.9996**, against
**0.0000** for the same arm cold in run (a). That is the cache condition moved
from one end of its range to the other on the same history, which is the whole
point of the warm arm and the thing the 2026-09-11 matrix could not do.

The overhead is what the plan predicted to the credit: **129 credits**
(516,251 uncached input at 250/1M, plus five output tokens), against a predicted
~129. And it is a real saving in the arm: the arm's own request 1 cost
**13 credits** warm against **129** cold, so warming pays for itself only if
something else reuses the primed prefix — which is exactly why priming is
reported as overhead rather than folded into the arm.

**Run (d) confirmed the warm-session prediction, and caught a harness bug on the
way.** The prediction was that priming the FULL history and then shaking it
would make the arm's request 1 **miss** and request 2 recover. Recomputed from
the request sequence, that is exactly what happened: request 1 is **152,185
input tokens with 9,216 cached — a fraction of 0.0606** — and request 2 is
**0.9585**. So a shake does invalidate a warm prefix, all but a fixed 9,216-token
head (the same 9,216 run 9 saw), and one request later the thread is fully warm
again. The cost of shaking a warm session is therefore **one** uncached request,
not a run's worth.

The live check said `NOT MET` and reported request 1 at 0.9585, which was wrong.
`shake` emits a `thread/tokenUsage/updated` carrying **no** input and **no**
output tokens — it is republishing the thread's recomputed size, not reporting a
request — and the runner counted it, pushing `firstArmRequestIndex` one request
too far and labelling the arm's own first request as priming. Fixed two ways:
the runner ignores a usage notification that carries no tokens and clears the
current turn id after priming, and every reporter derives the arm boundary from
the priming turns' own per-turn request counts
(`pricing_lib.first_arm_index`), which a notification outside a turn cannot
inflate. The recorded `cacheCondition` values are left as they were written and
the report recomputes and labels them, so the run does not have to be re-run:
0.0606 and 0.9585 **meet** the rule as stated, with request 1 just above the
0.05 bound because of that 9,216-token head.

## Does quota track total tokens or uncached tokens?

**It tracks total tokens.** This is the question the 2026-09-11 matrix could not
answer — both its arms sat at ~97.7% cached, so total and uncached moved together
(2.49x against 2.58x) and no arrangement of cold runs could separate them. The
warm condition separates them, and the answer is not close.

Every figure below includes the priming request, because it was paid. All five
deltas are **attributable**: no other personal-account session wrote a rollout
during any run.

| run | reqs | total input | uncached input | output | cached % | credits | **quota Δ** |
|---|---:|---:|---:|---:|---:|---:|---:|
| (a) full, cold | 49 | 27,202,610 | 599,602 | 19,934 | 97.8% | 840 | **+2 pp** |
| (b) shake, cold | 51 | 9,619,123 | 224,563 | 17,025 | 97.7% | 312 | **+1 pp** |
| (c) full, warm self | 57 | 31,379,338 | 589,706 | 17,014 | 98.1% | 938 | **+3 pp** |
| (d) shake, warm session | 65 | 13,632,344 | 766,168 | 27,160 | 94.4% | 547 | **+1 pp** |
| (e) shake, warm self | 60 | 12,276,949 | 256,981 | 24,781 | 97.9% | 396 | **+1 pp** |

Sorted by each candidate metric against the delta:

- **by total input** — 9.6M → +1, 12.3M → +1, 13.6M → +1, 27.2M → +2, 31.4M → +3.
  **Monotone, with no inversions**, at roughly **1 pp per 10M total input tokens**.
- **by credits** — 312 → +1, 396 → +1, 547 → +1, 840 → +2, 938 → +3. Also
  monotone, which follows: credits are dominated by the input term.
- **by uncached input** — 225k → +1, 257k → +1, **590k → +3**, **600k → +2**,
  **766k → +1**. **Badly non-monotone**, and the largest uncached spend in the
  batch bought the smallest delta.

The discriminating pair is **(c) against (d)**, and it is decisive:

| | (c) full, warm self | (d) shake, warm session |
|---|---:|---:|
| uncached input | 589,706 | **766,168** (30% MORE) |
| total input | **31,379,338** (2.3x more) | 13,632,344 |
| quota Δ | **+3 pp** | **+1 pp** |

(d) sent **30% more uncached input** than (c) and moved the window by **a third
as much**, while (c) sent **2.3x the total tokens**. A metering rule based on
uncached input has to predict (d) ≥ (c); the observation is the reverse, by 3x.
A rule based on total tokens predicts the entire ordering correctly.

**What this means for shake.** The saving is real in the metered unit and it is
the token reduction itself, not a cache effect: the shake arms sent a third of
the tokens and spent a third of the quota. Warming does **not** reduce quota —
(c) is the most expensive run in the batch precisely because priming added
516,251 tokens on top of a full-history arm — so a cache hit is a latency and
API-dollar optimisation, not a plan-quota one. On this account, **the only lever
on quota is how many tokens are sent at all**, which is exactly what shake moves.

**Limits, stated plainly.** n = 1 per cell and 1 pp is a coarse unit: 8 pp total
across 3,033 credits puts one percentage point at roughly **380 credits**, so
every delta here carries ±1 pp of quantisation and the three +1 pp rows
(9.6M, 12.3M and 13.6M total tokens) are genuinely indistinguishable from each
other. What the data supports is the **ordering** and the ruling-out of uncached
metering, not a coefficient. A second repetition of (c) and (d) would tighten it;
nothing else in this list would.
